## 設計規則

本章定義跨函式庫、作業系統介面與圖形 API 保持穩定的設計規則。每種執行機制都必須維持相同的責任歸屬、提交邊界、完成條件與資源所有權。

### 執行角色與責任

系統由一個協調角色與三類任務執行角色組成。協調角色只推進狀態；任務執行角色承擔會隨資料量或外部延遲成長的工作。協調角色以非同步方式提交工作，提交後立即繼續處理其他已就緒事件或返回中央事件等待；任務執行角色獨立推進工作，並以完成事件交回結果。

| 角色 | 唯一責任 | 對外交接 |
| --- | --- | --- |
| 主執行緒 | 序列化全域控制狀態，依已就緒事件決定下一個狀態轉移，並以非同步交接派發工作 | 工作描述、狀態授權或返回中央事件等待 |
| CPU 任務執行器 | 由多個 Workers 平行執行彼此獨立的 CPU 密集資料處理工作 | 完成結果與資源識別碼 |
| 儲存任務執行器 | 非同步執行目錄與檔案系統工作，讓多個已提交工作可同時等待或推進 | 標頭就緒、內容就緒或目錄就緒事件 |
| 圖形任務執行器 | 以圖形命令佇列非同步執行資源傳輸、繪製與畫面提交工作 | 傳輸完成、畫面完成或呈現額度事件 |

新增工作時，先依工作語意與狀態所有權決定唯一執行角色。全域控制狀態的判斷與轉移由主執行緒序列化；CPU 資料處理由 CPU 任務執行器承接；目錄與檔案系統工作由儲存任務執行器承接；資源傳輸、繪製與畫面提交由圖形任務執行器承接。同一張圖片仍依資料相依性跨階段交接；不同圖片可以分別位於儲存、CPU 與圖形階段，使三類任務執行角色同時工作。CPU 任務執行器內部再由多個 Workers 平行處理不同的工作描述。

成本來源用來驗證上述分工。主執行緒的每個控制步驟必須具有固定上界並直接返回；CPU 資料量、儲存延遲、圖形處理時間與各任務佇列深度都由對應任務執行器吸收。

大型資源由固定資源儲存區持續擁有。主執行緒與各任務執行器之間只傳遞工作描述、完成結果與資源識別碼；每次提交與對應的完成事件形成非同步邊界。提交立即返回主執行緒，任務執行器獨立推進工作，完成後以事件交回主執行緒，推進下一個控制狀態。

### 標頭優先的資源準備原則

首次接觸圖片時，儲存管線必須優先產生足以決定後續資源配置的標頭資訊。標頭資訊就緒後即可驗證格式、決定輸出尺寸與配置、保留記憶體額度並準備輸出資源；其餘檔案內容可在同一期間繼續讀取。

後續讀取同一張圖片且已保存的標頭資訊仍有效時，該資訊直接啟動資源準備，儲存任務執行器只需提供本次 CPU 工作所需的完整內容。這項原則由以下完成條件定義：

- 「標頭就緒」表示後續資源形狀已可決定。
- 「內容就緒」表示 CPU 工作所需的輸入內容已完整。
- 「資源就緒」表示輸出資源與記憶體額度已準備完成。
- 三項條件同時成立後，工作才具備進入 CPU 任務執行器的資格。

首次讀取時，標頭資訊與其餘檔案內容以非同步工作分成兩條可平行推進的邏輯路徑。兩項工作提交後，主執行緒立即繼續處理其他已就緒事件或返回中央事件等待；標頭路徑完成時，以事件推動格式驗證與輸出資源準備，內容路徑則持續取得 CPU 工作所需的完整輸入。兩條路徑的完成條件最後匯合，決定工作何時可以派發：

```text
圖片需求
├─優先取得標頭資訊─▶ 標頭就緒 ─▶ 驗證與準備輸出資源 ─▶ 資源就緒
└─取得其餘檔案內容──────────────────────────────────▶ 內容就緒

標頭就緒 ＋ 內容就緒 ＋ 資源就緒 ─▶ 可派發 CPU 工作
```

儲存介面可以依平台能力選擇請求數量、資料切割、對齊方式與完成通知機制。每種實作都必須保留上述三項完成條件，並維持資源準備與其餘內容讀取的重疊關係。

### 單張圖片的處理時序

```text
主執行緒          儲存任務執行器       CPU 任務執行器       圖形任務執行器
    │                    │                    │                    │
    │─提交讀取──────────▶│                    │                    │
    │◀─標頭就緒──────────│                    │                    │
    │─更新資源需求並推進資源準備              │                    │
    │◀─內容就緒──────────│                    │                    │
    │─派發 CPU 工作──────────────────────────▶│                    │
    │◀─CPU 工作完成───────────────────────────│                    │
    │─提交資源傳輸───────────────────────────────────────────────▶│
    │◀─資源傳輸完成───────────────────────────────────────────────│
    │─建立呈現授權並提交繪製─────────────────────────────────────▶│
    │◀─畫面完成或呈現額度─────────────────────────────────────────│
```

圖中的垂直順序只表示同一張圖片的資料相依性。每條「提交」或「派發」箭頭都在工作開始後立即結束本次主執行緒控制交易；對應的返回箭頭是稍後到達的完成事件。提交與完成之間，主執行緒處理其他已就緒事件或停留在中央事件等待，其他圖片則可以同時由儲存任務執行器、不同 CPU Workers 與圖形任務執行器推進。

角色間的交接契約由提交順序、完成順序與資料所有權構成；具體 API 與資料結構由實作層選擇。

### 主執行緒的控制邊界

主執行緒每次被事件喚醒後執行一個有界控制交易：取得固定額度的已就緒事件，依全域控制狀態決定狀態轉移，產生對應的工作描述或狀態授權，以非同步交接提交工作，然後立即繼續處理額度內的其他已就緒事件或返回中央事件等待。圖片呈現由主執行緒建立授權並提交圖形工作，實際繪製與畫面提交由圖形任務執行器完成。

中央事件等待是主執行緒唯一可長時間停留的位置。進入等待前必須釋放共享佇列的存取權；等待期間由作業系統掛起執行緒。主執行緒上的同步呼叫時間只能由記憶體內的小型控制狀態決定，並且與圖片大小、像素數、儲存延遲、圖形處理時間及 CPU 工作佇列深度無關。

每條新增呼叫路徑都必須記錄成本來源、任務執行角色、提交邊界及完成邊界。驗收分別記錄主執行緒累計 CPU 時間與單次控制步驟的最大經過時間，前者驗證總工作量歸屬，後者驗證單次事件處理的延遲上界。

## 目前實作對應

前章的設計規則是責任與完成條件的依據；本章將目前程式元件對應到各項設計角色與交接契約。

### 關係種類

```text
事件→ 外部輸入或非同步完成通知，經事件分派器送至固定事件處理流程
讀取→ 使用狀態或資料並保持原值
寫入→ 建立或取代狀態或資料
讀寫→ 讀取後修改同一狀態或資源
擁有→ 將狀態、資源生命週期或共享通道統一收納於單一資源擁有者
計算→ 產生本次同步呼叫使用的暫時選擇或順序，並保持持久狀態原值
判斷→ 依已讀取資料選擇控制分支，並保持持久狀態原值
呼叫→ 事件處理流程立即執行事件專用流程或共用流程
命令→ 呼叫固定成本的控制 API，並在同一個控制步驟內返回
提交→ 啟動外部非同步工作；完成後產生系統事件
```

事件參數攜帶事件來源資料；接收事件的處理流程從單一資源擁有者讀取其餘判斷所需的狀態與資源。單一資源擁有者保存事件處理流程與共用流程使用的全部可變狀態。

### 共用流程

圖中未加前綴的狀態與資源都位於同一個 `資源上下文` 內。

#### 重新計算緩衝需求

```text
[共用流程] 重新計算緩衝需求
│
├─讀取→ 圖片索引範圍
├─讀取→ 按住方向
├─讀取→ 最後有效導航方向
├─讀取→ 待完成短按承諾
├─讀取→ 長按 repeat 暫定終點
├─讀取→ 目前呈現索引
│
├─寫入→ 必須依序呈現範圍
├─寫入→ 解碼預取範圍
└─寫入→ GPU 預取範圍
```

輸入狀態、索引邊界及目前呈現位置決定導航授權與緩衝範圍；解碼結果決定圖片進入後續管線的時機。

#### 回收範圍外工作與 slots

```text
[共用流程] 回收範圍外工作與 slots
│
├─讀取→ 必須依序呈現範圍
├─讀取→ 解碼預取範圍
├─讀取→ GPU 預取範圍
├─讀寫→ 每張圖片的需求狀態與關聯 Slot ID
├─讀寫→ 工作佇列的生產端與工作取消旗標
├─讀寫→ 壓縮 PNG slot 狀態與可分配索引
├─讀寫→ 解碼 staging texture slot 狀態與可分配索引
├─讀寫→ GPU texture slot 狀態與可分配索引
├─讀寫→ 可呈現 GPU 圖片索引
├─讀寫→ staging 與 GPU 記憶體使用量
│
├─判斷→ 已要求且尚未取得 slot 的索引離開需求範圍
│   └─寫入→ 需求狀態為範圍外
├─判斷→ 壓縮 slot 正在接收檔案資料且索引已離開需求範圍
│   ├─寫入→ 壓縮 slot 為等待目前工作結束後回收
│   └─命令→ CancelIoEx
├─判斷→ 仍在工作佇列且索引已離開需求範圍
│   └─寫入→ 以工作項目的原子旗標取消；只有尚未被 Worker 取得時立即釋放資源
├─判斷→ Worker 已取出且索引已離開需求範圍
│   └─寫入→ 完成後可直接釋放
├─判斷→ 解碼 staging texture 位於保留範圍外且未被 Worker 或 GPU 使用
│   └─寫入→ staging slot 為可分配並加入可分配索引
└─判斷→ 可呈現 GPU 圖片位於保留範圍外且索引與目前畫面相異
    ├─寫入→ 從可呈現 GPU 圖片索引移除圖片
    └─寫入→ 對應 GPU texture slot 等待先前繪製完成後設為可分配並加入可分配索引
```

固定資源儲存區在整個工作階段持續擁有實體資源；回收時解除圖片與 Slot ID 的關聯並更新 slot 狀態。可分配索引專門提供可用 Slot ID；分配後的工作提交、完成處理與狀態轉換都直接攜帶 Slot ID。呈現時透過可呈現 GPU 圖片索引直接取得 GPU texture Slot ID。

#### 批次提交可執行的檔案讀取

```text
[共用流程] 批次提交可執行的檔案讀取
│
├─讀取→ 必須依序呈現範圍
├─讀取→ 解碼預取範圍
├─讀取→ 圖片路徑表
├─讀取→ 每張圖片的需求狀態與關聯 Slot ID
├─讀寫→ 壓縮 PNG slot 狀態與可分配索引
├─讀取→ 壓縮資料記憶體使用量
├─讀取→ 預估解碼輸出保留額度
├─讀取→ staging 記憶體額度
│
├─計算→ 範圍內已要求且尚未關聯任何 slot 的圖片
├─計算→ 必須呈現的相鄰圖片優先，其次才是預取圖片
├─判斷→ 對每個目前可容納的圖片
│   ├─寫入→ 取得可分配的壓縮 slot 並設為正在接收檔案資料
│   ├─寫入→ 保留預估解碼輸出額度
│   ├─寫入→ 圖片關聯壓縮 Slot ID
│   ├─判斷→ 標頭資訊狀態
│   │   ├─尚未取得 ─▶ 建立「標頭就緒」與「內容就緒」兩條邏輯路徑
│   │   └─已快取 ───▶ 直接沿用標頭資訊並建立「內容就緒」路徑
│   └─提交→ 符合標頭優先原則的 Windows 非同步檔案 I/O 工作描述
└─判斷→ 待讀需求已全部提交，或下一筆會超過記憶體或 slot 數量上限時結束
```

一般事件一次提交全部已取得 compressed reservation 且目前可執行的讀取；提交集合只由需求範圍、記憶體上限與壓縮 slot 數量上限共同決定。每張圖片的讀取工作描述必須遵守 [標頭優先的資源準備原則](#標頭優先的資源準備原則)。一般資料夾冷啟動在暫時 catalog 只有首圖，因此先提交首圖；目錄 I/O 完成並建立完整 reservation 後，同一次共用流程會派發所有能取得 compressed slot 與記憶體額度的 reservation。固定驗證清單也遵守相同規則。Direct3D、Direct2D、swap chain 與 back buffer 各初始化階段之間，已完成的 I/O 會先填充工作佇列，讓解碼與剩餘圖形初始化重疊；其餘初始化階段直接依序繼續。任何釋放 slot 或記憶體額度的事件都會再次呼叫本流程。

```text
├─讀取→ 工作描述指定的輸入資源 Slot ID
├─計算→ 工作描述指定的 CPU 密集階段
├─寫入→ 工作描述指定的輸出資源 Slot ID
├─讀寫→ 完成佇列的生產端
└─事件→ Worker 工作完成 [主事件迴圈]
```

目前工作佇列中的工作描述是 PNG 解碼：輸入為 Windows 非同步檔案 I/O 填入的壓縮 PNG slot，輸出為已映射的解碼 staging texture slot。

```text
[外部非同步執行器] Windows 非同步檔案 I/O
│
├─讀取→ `批次提交可執行的檔案讀取` 建立的檔案範圍、長度與目的緩衝區
├─寫入→ 壓縮 PNG slot 中對應的檔案內容範圍
├─事件→ 首次讀取的標頭資訊就緒 [主事件迴圈]
└─事件→ 完整內容就緒 [主事件迴圈]
```

目前 Windows 儲存介面的對應方式如下：

| 條件 | 目前機制 |
| --- | --- |
| Windows 11 | I/O Ring 與註冊緩衝區讀取描述 |
| Windows 10 | IOCP 與重疊式讀取要求 |
| 首次讀取 | 優先讀取足以決定 PNG 輸出資源的標頭範圍，並同時讀取其餘內容 |
| 標頭資訊已保存 | 沿用既有標頭資訊並提交完整內容讀取 |

首次讀取的標頭範圍至少涵蓋目前 PNG 解析器判斷輸出資源所需的 24 位元組，並依底層儲存介面的 I/O 對齊單位向上對齊。分割後的檔案範圍完整覆蓋本次內容且彼此互斥。這些數值與 API 屬於目前 Windows／PNG 配接層；設計層的要求是「標頭就緒、內容就緒、資源就緒」三項完成條件及其重疊關係。

```text
[外部非同步執行器] GPU 命令佇列
│
├─讀取→ GPU 上傳工作指定的解碼 staging texture slot
├─寫入→ GPU 正在寫入的 GPU texture slot
└─事件→ GPU 上傳完成 [主事件迴圈]
```

```text
[外部事件來源] DXGI SwapChain
│
└─事件→ Frame 提交額度可用 [主事件迴圈]
```

工作佇列與完成佇列是主執行緒和 Workers 之間的共享通道。工作項目的原子旗標協調「等待領取、已由 Worker 取得、已取消」；完成佇列由多個 Worker 寫入、主執行緒排空。工作只攜帶工作種類與 Slot ID；固定資源儲存區保持資源位址與所有權穩定，slot 狀態授權單一 Worker 在 CPU 密集工作期間讀寫指定資源。

### 設計符合狀態

「設計規則」是目標契約；本表分別標示已落實、待完成與待確認項目。

| 設計要求 | 目前狀態 | 對應位置或待完成事項 |
| --- | --- | --- |
| CPU 密集工作由 Workers 執行 | 已符合 | PNG 解碼經工作佇列派發 |
| 檔案內容由非同步儲存介面讀取 | 已符合 | I/O Ring 或 IOCP |
| 標頭優先推動資源準備 | 已符合 | 標頭完成事件先建立 staging resource |
| 檔案 handle 建立與儲存中繼資料查詢由儲存任務執行器承接 | 待完成 | `CreateFileW`、`GetFileSizeEx` 與 `GetFileInformationByHandleEx` 目前在主執行緒同步執行 |
| 圖形 API 提交具備固定的主執行緒時間上界 | 待確認 | `CreateTexture2D`、`Map`、繪製提交與 `Present` 目前由主執行緒呼叫，需量測單次最大時間並確認驅動程式同步成本 |

### 實作約束

事件分派器依事件種類選擇唯一的事件處理流程。Windows 訊息按固定額度處理；完成事件必須依「設計符合狀態」補上有界批次後，才能滿足固定額度要求。事件處理流程的責任範圍是讀寫控制狀態、規劃需求、建立呈現授權及提交工作。

資源上下文由主執行緒擁有，集中保存可變控制狀態、資源生命週期、固定資源儲存區及索引。主執行緒是工作佇列的生產者與完成佇列的消費者；Workers 是工作佇列的消費者與完成佇列的生產者。每一端只修改自己的佇列端點及目前工作項目的原子交接狀態。

各類資源的寫入授權如下：

| 資源 | 唯一內容寫入者 | 後續讀取者 |
| --- | --- | --- |
| 壓縮資料 slot | Windows 非同步 I/O | 單一 Worker |
| 解碼 staging slot | 單一 Worker | GPU |
| GPU texture slot | GPU | Direct2D |

slot 狀態是資源能否分配的權威來源。可分配索引只保存可分配的 Slot ID；工作、完成結果與狀態轉移直接攜帶 Slot ID。可呈現圖片索引保存「圖片索引到 GPU texture Slot ID」的直接對應。

每張圖片同時最多有一條檔案讀取流程與一條 CPU 解碼流程。取消後依目前索引狀態與需求範圍重新決定是否派發。檔案讀取由需求範圍選取，並受固定記憶體額度與壓縮資料 slot 數量限制；每次批次提交目前所有可執行的 reservation。

解碼 staging slot 依序經過「已準備、Worker 獨占寫入、解碼完成、GPU 來源、可分配」階段。GPU texture slot 由固定資源儲存區持續擁有，並依序經過圖片關聯、繪製完成與可分配階段。

輸入事件建立呈現授權，每份授權依相鄰圖片順序獲得獨立呈現機會。每個 Windows repeat 最多建立一份暫定授權；方向鍵放開時捨棄待呈現的 repeat 授權並保留短按承諾。每份 DXGI 畫面額度最多推進一張圖片，推測性解碼與 GPU 預取則提前準備後續呈現所需資源。
